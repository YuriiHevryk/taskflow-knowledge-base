# Онтологія TaskFlow

## 1. Типи сутностей

У базі знань TaskFlow використовуються такі типи сутностей:

- concept - поняття предметної області.
- component - програмний компонент застосунку.
- decision - архітектурне рішення.
- glossary - визначення термінів.
- moc - навігаційна нотатка.
- ontology - опис структури знань та відношень.

Тип сутності визначається полем type у YAML frontmatter.

## 2. Типи зв'язків

### depends_on

Означає залежність одного програмного компонента від іншого.

Приклад:
[[Task Service]] залежить від [[Task Repository]].

### represents

Означає, що компонент представляє певне поняття предметної області.

Приклад:
[[Task Model]] представляє [[Task]].

### governed_by

Означає, що реалізація компонента визначається певним архітектурним рішенням.

Приклад:
[[Task Repository]] керується рішенням [[SQLite Storage Decision]].

### supersedes

Означає, що нове архітектурне рішення замінює попереднє.

Використовується, якщо під час розробки змінюється раніше прийняте рішення.

## 3. Конвенція запису зв'язків

Типізовані зв'язки записуються у YAML frontmatter.

Приклад для Task Service:

depends_on:
  - "[[Task Repository]]"
  - "[[Task Model]]"

Приклад для Task Model:

represents:
  - "[[Task]]"

Приклад для Task Repository:

governed_by:
  - "[[SQLite Storage Decision]]"

Для кожного зв'язку вказується тип відношення та назва цільової нотатки.

Wiki-посилання у тексті нотаток залишаються для зручної навігації.

## 4. Правила підтримки онтології

- Кожна змістовна нотатка повинна мати властивість type.
- Для класифікації використовуються теги.
- Назви цільових нотаток мають відповідати наявним файлам.
- Для залежностей між компонентами використовується depends_on.
- Нові архітектурні рішення не повинні видаляти історію попередніх рішень.
- Головна карта знань зберігається в [[MOC-TaskFlow]].
