# User Settings Storage

# Architecture Decision: User Settings Storage

**Статус: Запропоновано — не затверджено.**

### Context

TaskFlow — локальний CLI-застосунок на Python. Вимоги передбачають збереження **завдань** у SQLite, але не визначають типи, обсяг чи правила зберігання **налаштувань користувача**. Наявне рішення [[SQLite Storage Decision]] стосується сховища завдань; його не слід автоматично поширювати на налаштування.

Окремого компонента налаштувань у перевірених вимогах і знайдених Python-файлах немає. Тому рішення про формат сховища запропоноване за поточним припущенням: налаштування невеликі, локальні й не потребують складних запитів. Якщо це припущення хибне, рішення варто переглянути.

### Alternatives

**1. JSON-файл у каталозі конфігурації користувача**

- **Переваги:** простий формат; не потребує бібліотек чи окремого сховища; зручно читати, переносити й резервувати невеликий набір налаштувань; відокремлює конфігурацію від даних завдань.
- **Недоліки та ризики:** потрібні явна перевірка структури й обробка помилкового JSON; формат і набір полів можуть змінюватися; перерване перезаписування може пошкодити файл, тому запис варто виконувати атомарно.

**2. Таблиця налаштувань у SQLite**

- **Переваги:** транзакційне оновлення; схема й обмеження даних; налаштування потрапляють до спільного резервного копіювання бази.
- **Недоліки та ризики:** налаштування стають залежними від життєвого циклу й міграцій бази завдань; для простих локальних параметрів це додає зв’язність і складність без визначеної потреби в SQL-запитах чи транзакціях.

### Decision

**Запропоновано** зберігати налаштування користувача в окремому JSON-файлі в користувацькому каталозі конфігурації. Налаштування не зберігатимуться в SQLite і не змінюватимуть спосіб зберігання завдань.

Під час реалізації слід визначити розташування файлу, перевіряти його структуру, зберігати невідомі параметри без мовчазного пошкодження даних і записувати зміни атомарно. Помилки читання чи некоректний вміст мають повідомлятися явно, а не приховуватися.

### Rationale

Наразі єдина вимога щодо SQLite стосується завдань. Для невеликого локального набору налаштувань не виявлено потреби в реляційних запитах або спільних транзакціях із завданнями. JSON дає змогу зберегти просту межу між конфігурацією та предметними даними, не додаючи окремої системи чи залежностей.

Рекомендація спирається на припущення про прості налаштування. Якщо з’являться вимоги до складних зв’язків, транзакційної узгодженості з даними завдань або активної підтримки багатьох користувачів, варіант із SQLite слід оцінити повторно.

### Consequences

- Налаштування матимуть окремі від бази завдань місце зберігання та резервного копіювання.
- Доведеться реалізувати перевірку формату, сумісність зі змінами структури та безпечний запис файлу.
- Рішення про SQLite для завдань залишається чинним і не змінюється.
- Потреба в окремому компоненті налаштувань і його відповідальності має бути уточнена під час реалізації.

- [[Task Repository]] — продовжує відповідати за дані завдань; зберігання налаштувань не пропонується додавати до нього.

### Verification

Перед затвердженням рішення слід перевірити:

- читання, запис і повторне завантаження налаштувань;
- поведінку за відсутнього файлу та коректне застосування початкових значень;
- явне повідомлення про некоректний JSON або невалідну структуру без автоматичного затирання файлу;
- атомарність запису;
- незалежність від CRUD-операцій завдань у SQLite та від наявного [[SQLite Storage Decision]].
